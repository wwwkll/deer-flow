## 一、双轮 audit 全章重审 — 设计保留，但记录优化方向

### 现象

写作流水线设计：write → audit → 若 FAIL 则 revise → audit 再跑一遍 → world-updater。两轮 audit 都是**整章从头审**：

```
audit#1 (章57)  3.9 min
audit#2 (章57)  5.6 min    ← 修过之后第二轮反而更慢
audit#1 (章60)  8 min
audit#2 (章60)  12 min 45 s  ← 70 条消息，最大耗时点
```

控制逻辑在 [backend/packages/harness/deerflow/workflows/novel_writing.py:368-373](../../backend/packages/harness/deerflow/workflows/novel_writing.py:368)：

```python
def should_revise(state):
    if state.get("audit_passed"):
        return "post_process"
    if state.get("audit_round", 0) >= 2:
        return "post_process"
    return "revise"
```

最多 2 轮 audit，第二轮的成本来自：完整重读正文、伏笔池、人物档案、世界观，所有维度全跑一遍。

### 决策

**保留不改**（设计如此，质量优先）。

### 未来如想优化（仅作参考，不必立即实施）

- **差分 audit**：给第二轮传 reviser 写出的"修改记录"，只复检修过的段落和这些段落涉及的连贯性，跳过未触碰部分。
- **轻量审核模型**：第二轮换更小/更快的模型（仅做格式、字数、错别字等机械检查），把语义连贯性留给第一轮。
- **跳过 round 2**：若 round 1 的 issues 仅为 minor（如字数差几十、个别错字），跳过 round 2 直接进 world-updater。需要改 `_parse_audit_result` 让它返回严重度等级，而不仅仅是 PASS/FAIL。

## 二、本地模型频繁产生 dangling tool calls（24 次/日志窗口）

### 现象

```
[warning] Injecting 3 placeholder ToolMessage(s) for dangling tool calls
```

整份日志中出现 **24 次**。每次表示本地模型 `qwen-3-6-local`（`http://192.168.31.187:1234`）输出了无效的 `tool_call`（结构不完整、tool_call_id 对不上、或多个 call 没全部返回），系统不得不注入 3 个空占位 `ToolMessage` 让模型继续。每次 ≈ 一次完全浪费的 LLM 调用 + 一次模型重生成。

### 触发位置

[backend/packages/harness/deerflow/agents/middlewares/dangling_tool_call_middleware.py](../../backend/packages/harness/deerflow/agents/middlewares/dangling_tool_call_middleware.py)

### 影响

- 每章约 4-6 次 dangling，等价多花 4-6 个 turn（每 turn 本地模型约 2-7 秒）。
- 累计影响：单章额外耗时 30 秒 ~ 1 分钟。

### 建议

1. **强化本地模型 system prompt 中关于 tool_call 格式的约束**。检查 [backend/packages/harness/deerflow/agents/lead_agent/prompt.py](../../backend/packages/harness/deerflow/agents/lead_agent/prompt.py) 是否有专门给本地模型的 prompt 模板。
2. **减少占位符数量**：当前是 "3 placeholder"，可以改成只注入实际 dangling 数量对应的占位符（如果模型只发了 1 个 tool_call 但回包没接住，就只注入 1 个）。看 middleware 是否硬编码了数量。
3. **告警阈值**：如果同一 run 内 dangling 次数 > 5，提前终止并报告用户，避免一直在跑无效轮次。

### 优先级

**P1**。本地模型环境下能直接救出每章 30 秒以上。

## 三、`task_tool` 5 秒 polling 间隔造成 ~1-2 min/章 空转

### 现象

通过 `task` 工具调用子 Agent 时，子 Agent 已经 captured AI message，但 task_tool 要 ≈ 5 秒后才把消息送给父 Agent：

```
12:36:25.557 [trace=95dd7639] Subagent novel-reviser captured AI message #1
12:36:30.379 [trace=95dd7639] Task 118983389 sent message #1/1      ← 5 秒延迟
```

启动时日志：

```
Started background task 118983389 (subagent=novel-reviser, timeout=1800s, polling_limit=372 polls)
```

`1800s / 372 polls ≈ 4.84s/poll`。

### 触发位置

[backend/packages/harness/deerflow/tools/builtins/task_tool.py](../../backend/packages/harness/deerflow/tools/builtins/task_tool.py)（推测，需确认）

### 影响

- 单章流水线 ≈ 12-27 个子 Agent turns，光是 polling 等待就 1-2 分钟纯空转。
- 流水线越长，浪费越显著。

### 建议

1. 把 `polling_interval` 改成 1 秒（仍保留 1800 秒总 timeout，相当于 polling_limit 改成 1800）。
2. 更彻底：**改成事件驱动**——子 Agent 每捕获一条 AI message 直接 push 到父 Agent 的 message queue，去掉 polling。

### 优先级

**P1**。改 polling_interval 是单行修改、低风险，收益明确。

## 四、checkpointer 缺 `aprune` — 长期会让 PostgreSQL checkpoint 表无限增长

### 现象

每次 langgraph 启动都打印 warning：

```
[warning] Custom checkpointer missing aprune: thread history pruning 
(keep_latest) is not supported. Old checkpoints will accumulate and 
storage usage will grow without bound for long-lived threads.
```

同时还少了 `adelete_for_runs`（cancelled runs 的 checkpoint 不会清理）和 `acopy_thread`（fallback 到逐条 re-insert，但 copy 操作罕用，影响小）。

### 触发位置

[backend/packages/harness/deerflow/agents/checkpointer/async_provider.py](../../backend/packages/harness/deerflow/agents/checkpointer/async_provider.py)

### 影响

- **写一本 60 章的书**：约 60 次 writer + 60 次 audit + 60 次 reviser + 60 次 world-updater = 240 次子 Agent run，每次都产生十多个 checkpoint。一本书估计 3000+ checkpoint 条目堆在 PostgreSQL 里。
- 长 thread 的 history 加载会越来越慢。
- 取消的 run（用户点了停止）的 checkpoint 永远留着。

### 建议

1. 在 `async_provider.py` 实现 `aprune(thread_id, keep_latest)` 方法，按时间排序保留最近 N 个 checkpoint，删除其余。
2. 顺手实现 `adelete_for_runs(thread_id, run_ids)`，删除指定 run 的 checkpoint。
3. 可以参考 langgraph 官方 `AsyncPostgresSaver` 的同名方法实现。

### 优先级

**P2**。短期没事，但 thread 越用越慢的体感会在用户那边累积出来。建议在下一次 PostgreSQL 维护窗口一起做。

## 五、context window 自动检测 1 秒超时太短

### 现象

```
Could not auto-detect context_window from https://8sk407kn4499.vicp.fun/v1/models 
(timeout=1s)
```

后续 fallback 到 32768。但 `qwen-3-6-online` 实际 context 可能更大。fallback 后的副作用：

```
Resolved trim_tokens_to_summarize fraction 0.85 -> 27852 (context_window=32768)
```

意味着对话超过 27852 token 就开始 summarization，比应有阈值更早触发。

### 触发位置

[backend/packages/harness/deerflow/agents/lead_agent/agent.py:323](../../backend/packages/harness/deerflow/agents/lead_agent/agent.py:323) 附近，搜 `auto-detect context_window` 或 `timeout=1s`。

### 影响

- 在线模型下：summarization 提前触发，频率过高，浪费 LLM 调用。
- 用户体感：对话才聊几轮就被压缩，前文细节丢失。

### 建议

1. **提高 timeout**：从 1s 改成 5s，足够 `/models` 接口正常响应。
2. **缓存检测结果**：第一次成功探测后写入磁盘/内存，避免每次启动都探测。
3. **手动覆盖优先**：允许在 [config.yaml](../../config.yaml) 的 model 配置里手动写 `context_window: 65536`，跳过自动检测。看代码当前是否已支持这个字段（按 [config.example.yaml](../../config.example.yaml) 第 272 行 summarization 注释，"也可在模型配置中手动指定 context_window 字段"——若支持，写文档提醒用户配置）。

### 优先级

**P2**。在线模型用户能感觉到，但不致命；本地模型按 70000 走的，不受影响。
